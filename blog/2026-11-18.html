    #我把六种运行时塞进了同一个文件夹

    我换过几次电脑。每次开机第一件事都差不多：下 Python，下 Node，配 PATH，想起来 Go 还没装，再想起来 JDK 也得有。

    装的时候没觉得有什么，卸载的时候才热闹。注册表里留一堆键，用户目录里留几个隐藏文件夹，加起来好几个 G，而你并不确定哪个能删。

    后来我就想，这些东西的官网其实都给了压缩包。解压就能跑。那为什么不干脆全塞进一个目录，用的时候叫一声？

    EnvXX 就是这么来的。

    envxx python3.11 -m pip install requests
envxx node22 -v
envxx go1.27 version

    ~/.envxx 是唯一新增的东西。想清干净，删掉它。

    #先把边界划清楚

    它不解决依赖问题。

    不编译源码，不解析依赖树，也没有 lockfile。你让它装 Python，它就去 python-build-standalone 下一个官方构建，解开，记住在哪，下次你叫它的时候把命令转发过去。

    pip 和 npm 该干的活它一点没碰。EnvXX 管的是"这个工具本身装在哪"，pip 管的是"这个工具里面装什么"。两边各管一摊，谁也不越界。

    我觉得这个界限还挺重要的。见过太多工具，一开始只是帮人装个运行时，后来觉得自己也能管依赖，再后来就有了自己的 lock 格式和镜像源，最后变成一个更烂的版本管理器。

    #免安装版不是洁癖

    因为安装程序和"删掉就能清干净"天然冲突。

    msi 会往注册表写，pkg 会往 /Library 里塞，发行版的包管理器倒是规矩，但你得先有 root。而这些工具的官方发布页早就放过 zip 和 tar.gz 了，只是没人愿意自己处理那些包。

    处理它们确实烦。顶层有目录的、没目录的、二进制在 bin/ 的、在根目录的、在 Contents/Home/bin/ 的，Windows 上多个 .exe，macOS 上多个 bundle。你最想要的那个入口，通常不是包里最显眼的那个。

    这些差异都埋在代码里了。前面那行 envxx go1.27 version，你不需要知道 Go 的包顶层目录叫 go。

    #加 Go 之前我以为会很简单

    确实简单。go.dev 给了个 JSON 清单，每个文件自带 sha256，连校验文件都不用单独去下。

    {"version": "go1.27.4", "files": [
  {"filename": "go1.27.4.windows-amd64.zip", "os": "windows",
   "arch": "amd64", "kind": "archive", "sha256": "73cfb8..."}
]}

    过滤 kind == "archive"，按 os 和 arch 匹配，就完事了。同一个清单里还有 installer 类型的 msi，别选错。

    麻烦的是看起来最标准的那一个：JDK。

    #JDK 让我重新认识了"官方包"

    Adoptium 有三套版本字段。

    同一个 27 的构建，有的报 openjdk_version: "27.0.1.0"，四段；有的报 "27+35"，两段。你没法用一个正则同时处理。翻了半天发现 semver 字段倒是稳定，永远三段加元数据，剥掉 + 后面的就行，openjdk_version 留着兜底老 payload。

    然后是包结构。我按 bin/java 写的第一版，Windows 上跑得挺好。后来不想赌，下了 Linux 和 macOS 的 tarball，各读头几兆解包看了一眼。

    Linux 是 jdk-21.0.13+9/bin/java，正常。macOS 是：

    jdk-21.0.13+9/Contents/Home/bin/java

    多两层。

    如果没看这一步，Windows 的测试会全绿，macOS 用户会拿到一句 has no java。这类问题只有真去解包才会暴露，猜是猜不出来的。

    顺便说，JDK 的包是真大，21 那个压缩完 205MB，解开 328MB。装的时候看着进度条会有点怀疑人生。

    #Bun 的 bunx 在官方包里不存在

    这个纯粹是我想当然。

    照着 npm 的习惯，我在配置里写了 bun 和 bunx 两个入口。装完一跑：

    error: bun 1.4.4 has no bunx at ...\bunx.exe

    去包里看，就一个 bun.exe。bunx 是 npm 安装时创建的符号链接，官方 zip 里压根没有。

    删掉那行配置就好。bun x 本来就等价，功能上没损失。但这提醒我，配置得对着包结构写，不能对着记忆写。

    #装进 Python 里的命令，一开始叫不动

    我自己装完之后想运行刚装的东西：

    envxx python3.11 pip install -e .
envxx python3.11 envxx

    第二条直接报错：

    can't open file '...\envxx': [Errno 2] No such file or directory

    原因是 envxx 不在我声明过的入口里，于是整串被当成参数传给 Python，Python 就去打开一个叫 envxx 的源文件。

    修法是让配置声明哪些目录可能会有控制台脚本（Python 是 Scripts/ 和 bin/），调用时按名字去找。找到就走脚本，找不到还是原样当参数，这样 envxx python3.11 script.py 的行为一点不变。

    顺手加了个名字白名单。../outside 这种拼法进不来。

    #CI 上只有 Windows 会犯的错

    打包之后要从 dist/ 里挑二进制，原来是这么写的：

    bin=dist/envxx
[ -f "$bin" ] || bin=dist/envxx.exe

    在 Windows 的 Git Bash 里，test -f dist/envxx 对 dist/envxx.exe 也返回真。于是变量停在了不带扩展名的路径上，后面 basename 拿到的也是 envxx。

    结果就是 Windows 的发布包里躺着一个叫 envxx 的文件，没后缀，双击打不开。

    改成先判断 .exe 就行了。但这属于只在特定 shell 里成立的隐式行为，不实际跑一遍根本发现不了，而且 CI 绿了你也不会去看 zip 里到底叫什么。

    #列表顺序，以及一个指错方向的提示

    做之前的状态是乱的：运行时升序，旧的在上；应用降序，新的在上。因为命令行里对 app 单独反转了一次。

    顺手改的时候发现了另一个问题。update 之后的提示长这样：

    older versions still on disk: 22.14.0, 20.19.0 (envxx node rm 22.14.0 to remove)

    看着挺合理。但 older[0] 取的是列表第一项，而那个列表当时是降序拼接的，也就是说它指向最旧的那个。你刚升到最新版，它建议你删掉最老的，把中间那个留着。

    现在排序收进了基类，只在一个地方发生。older 整体降序，older[0] 就是次新版。

    还有个更隐蔽的。命令行原来这么判断：

    if all_versions and hasattr(provider, "search_all"):

    一半的 provider 有这个方法，一半没有。但没那个方法的会回落到 display_versions()，而那东西对按版本线折叠过的工具返回的是折叠结果。所以对 Go、JDK 这些新加的工具，search --all 和 search 输出完全一样。

    hasattr 本身就是个信号。如果一个方法该有一半没有，那说明它应该在基类。

    前六个是运行时，可以多版本并存；后面几个是应用，留一个最新的就够。

    #打包这摊事

    打 v* 的 tag 会触发 Actions，六个平台各打一个 PyInstaller 单文件，再包成带版本号的 zip：

    1.0.7-windows-x64.zip  →  1.0.7-windows-x64/envxx.exe
1.0.7-linux-x64.zip    →  1.0.7-linux-x64/envxx

    zip 里写了 Unix 权限位，unzip 出来的 Linux 和 macOS 二进制本来就可执行。

    PyInstaller 不能交叉编译，每个平台在自己 runner 上跑。Linux 特意选 22.04 而不是最新的 24.04，这样 ELF 只要求 glibc 2.35，老一点的发行版也能跑。这个细节是从之前打包的经验里带过来的，选错版本号，用户那边会报 GLIBC_2.39 not found，而你本地永远复现不了。

    代码在 mikigo/EnvXX，发布页有六个平台的压缩包，解压改名放进 PATH 就能用，不需要先装 Python。

    ripgrep、fd、fzf 这些单文件工具还在候选名单里。哪天用到了再加，反正加一个工具只是填一个 provider。
