    #我花了三天时间，让 Claude Code 帮我写了一个网站计数器，然后把它开源了

    #背景

    事情的起因很简单：我的个人站点 mikigo.site 是用 Rspress 搭建的纯静态博客，没有后端，自然也就没有访问统计。我想知道哪篇文章最受欢迎、每天有多少人来看，但又不愿意接入 Google Analytics——那玩意儿一个脚本 100KB，还要弹 Cookie 弹窗，对技术博客来说实在太重了。

    市面上倒是有不蒜子这类轻量方案，但服务是别人维护的，数据存在别人服务器上，哪天说不蒜就不蒜了。

    于是我问了自己一个问题：能不能自己写一个？

    能。尤其是当你有一个 Claude Code 在旁边的时候。

    #技术选型：够用就好，别想太多

    计数器这个需求本身很简单——记录访问、查询统计、展示数据。技术选型上我给自己定了三条原则：

    1. 依赖最小化——能用一个库解决的绝不引入第二个
    2. 运维零负担——不需要 MySQL、Redis、消息队列，一个 SQLite 搞定
    3. 部署一条命令——用户 pip install && web-counter start 就能跑起来

    最终选型如下：

    层选择理由
    Web 框架FastAPI + uvicorn异步支持好，BackgroundTasks 适合异步写库
    数据库SQLite (WAL) + aiosqlite单文件零配置，WAL 模式支持并发读写
    密码哈希bcrypt业界标准，Dashboard 管理员密码存储
    前端 JS原生 JavaScript（~1KB）不引入任何框架，兼容所有浏览器
    图表Chart.js CDNDashboard 看板的 30 天趋势图，CDN 引入不占包体积
    进程管理systemd + PID 文件start / stop / restart 命令行管理
    分发pip 包（PyPI）标准 Python 分发方式

    是的，你没看错——没有 React、没有 Vue、没有 Webpack。前端 counter.js 只有约 1KB，用原生 XMLHttpRequest 发两个请求，剩下的交给 DOM API。对于一个计数器来说，这就够了。

    #架构设计：麻雀虽小，五脏俱全

    ┌──────────────────────────────────────┐
│           用户的静态网站                │
│  <script src="/counter.js">          │
│  <span data-pv-site></span> 次       │
└──────────────┬───────────────────────┘
               │ HTTPS
┌──────────────▼───────────────────────┐
│         Caddy / Nginx 反代            │
│  /counter.js  →  web-counter:8000    │
│  /api/*       →  web-counter:8000    │
│  /*           →  静态文件              │
└──────────────┬───────────────────────┘
               │ localhost
┌──────────────▼───────────────────────┐
│          web-counter (FastAPI)        │
│  ┌─────────────────────────────┐    │
│  │ counter.js  │  REST API     │    │
│  │ Dashboard   │  Rate Limiter │    │
│  └─────────────┴───────────────┘    │
│              SQLite (WAL)            │
└──────────────────────────────────────┘

    核心设计决策有三条，每条背后都有故事：

    1. 自动发现 API 地址。counter.js 通过 document.currentScript.src 反推 API 基地址，用户不需要配置域名。同域部署时开箱即用，跨域时通过 data-counter-api 属性指定。

    2. 声明式 DOM 绑定。用户只需在 HTML 中写 <span data-pv-today></span>，counter.js 自动扫描 data-* 属性并填充数据。计数器容器初始 display:none，只有成功获取数据后才显示——后端挂了用户完全无感。

    3. 隐私优先的访客去重。不存 IP、不设 Cookie、不做指纹。访客唯一性由 SHA256(IP + salt) 标识，salt 由部署者自己生成和保管。换 salt 意味着历史 UV 清零，所以文档里写了三遍"salt 设定后不要更换"。

    #前端 counter.js：1KB 的自我修养

    // 整个脚本的核心逻辑就三步
(function () {
  // 1. 发现 API 地址
  var apiBase = scriptTag.src.substring(0, scriptTag.src.lastIndexOf("/"));

  // 2. 扫描 DOM
  var pvToday = document.querySelector("[data-pv-today]");

  // 3. 发请求 + 填数据
  xhr.open("GET", apiBase + "/api/count");
  xhr.onload = function() {
    pvToday.textContent = JSON.parse(xhr.responseText).today_pv;
    container.style.display = "inline-block"; // 大功告成
  };
})();

    当然，实际代码比这复杂一些，因为要处理千分位格式化、多种展示风格（badge / card / bordered）、SPA 客户端路由（MutationObserver）、多容器可见性等等。但核心理念不变：简单的需求就应该用简单的代码解决。

    展示风格也是用内联 CSS 实现的，没有额外的样式文件。用户通过 data-counter-style 属性选择：

    风格效果
    badge圆角药丸徽章，GitHub 风格
    card白底卡片 + 阴影
    bordered细边框方框
    default纯文本

    #部署实录：从本地到云端

    #服务器环境

    • Ubuntu 22.04，Caddy 做 Web 服务器和 HTTPS
    • Python 3.10，pip 安装 web-counter
    • SQLite 数据文件在 /opt/web-counter/data/

    #systemd 守护

    [Service]
Type=simple
Environment="COUNTER_SALT=<密钥>"
Environment="COUNTER_HOST=127.0.0.1"
Environment="COUNTER_PORT=8001"
ExecStart=python3 -m uvicorn web_counter.main:app --host 127.0.0.1 --port 8001
Restart=on-failure

    关键：绑 127.0.0.1，不直接暴露公网。所有请求通过 Caddy 反代进来。

    #Caddy 反代

    mikigo.site, www.mikigo.site {
    handle /counter.js { reverse_proxy 127.0.0.1:8001 }
    handle /api/*      { reverse_proxy 127.0.0.1:8001 }
    handle /dashboard  { reverse_proxy 127.0.0.1:8001 }
    root * /var/www/mikigo.site
    file_server
}

    同域部署不需要 CORS 配置，这是最简单的方案。

    web-counter 自身也在同一台服务器上，通过 systemd 管理生命周期。

    #Dashboard：登录即用的统计看板

    /dashboard 提供了完整的后台管理界面：

    • 实时统计卡片——今日 PV/UV、累计 PV/UV，每 30 秒自动刷新
    • 30 天趋势图——Chart.js 折线图，PV 和 UV 双线对比
    • 排行榜管理——配置显示数量、排除规则（支持 * 通配符）
    • 数据管理——重置全部/今日/指定页面数据，设置累计起始值

    后台密码用 bcrypt 哈希存储，登录后签发 HttpOnly + SameSite=Lax 的 session cookie，24 小时过期。

    #Agent Skill：让 AI 帮你集成

    开发过程中踩了不少框架特有的坑，我把它们全写成了 Claude Code Skill，这样其他人在 AI 辅助下集成时能自动避开：

    Skill适用框架
    rspress-web-counterRspress 集成全流程
    vitepress-web-counterVitePress 集成全流程

    Skill 涵盖了所有已知的坑：

    • Rspress head 配置 async:true 会被序列化成 asyncsrc（属性粘连 bug）
    • JSX 中 <span data-pv-page> 会渲染成 data-pv-page="true"
    • VitePress footer 在所有页面渲染（与 Rspress 不同）
    • 等等

    #我们踩过的 8 个坑

    整个项目用 Claude Code 辅助开发，三天时间写完、测试、部署、上线。过程并非一帆风顺，以下是印象最深的几个问题：

    1. Rspress head 布尔属性序列化 bug

    在 head 配置中写 ['script', { async: true, src: '/counter.js' }]，Rspress 渲染成了 <script asyncsrc="/counter.js">——async 和 src 粘连了。浏览器不认 asyncsrc，脚本压根没加载。解决：去掉 async: true，只用 { src: '/counter.js' }，或者将 script 放在 footer message 的原始 HTML 中。

    2. React JSX 属性值陷阱

    <span data-pv-page></span> 在 JSX 中会被 React 渲染为 data-pv-page="true"，counter.js 读到 "true" 当作页面路径，导致阅读量查询错误。解决：写 <span data-pv-page=""></span>（空字符串）。

    3. SPA 客户端路由计数器消失

    Rspress 页面切换时 footer 被重新渲染（display:none），但浏览器不重新执行 <script> 标签。解决：v0.2.0 引入 MutationObserver，监听 DOM 变化自动重新填充计数器。

    4. 首次刷新 +2 计数

    DOMContentLoaded 触发一次 refresh()，MutationObserver 检测 DOM 插入后又触发一次。解决：加 800ms 冷却期 + 路径去重。

    5. 首次访问显示 0

    counter.js 同时发 visit 和 count 请求，visit 异步写库还没完成 count 就返回了。解决：先发 visit → 等完成 → 再发 count。

    6. 多容器只显示一个

    页面同时有 footer 统计和文章阅读量两个 counter-container，早期代码只处理第一个。解决：遍历所有 counter 元素，每个容器独立显示。

    7. 排行榜标题缺失

    全新页面无 title 历史数据，排行榜只显示 URL。解决：counter.js 上报时附带 document.title，服务器存到 page_titles 表；同时也批量从 HTML 文件中提取 titles 补全历史数据。

    8. Rspress footer 只在首页

    themeConfig.footer.message 在 Rspress 中仅在首页渲染，文章页没有。解决：全站统计数据放在 footer 中（首页可见），页面阅读量放在 afterDocContent 中（文章页可见）。
